# REQ-261027 — 콘솔: 상담원·고객 식별 표시 (라이브챗·작업로그·고객·대화 이력)

## 요구사항 (2026-10-27)
**/live-chat**
- R1 대화방을 열면 가장 최근 대화가 보여야 한다(맨 아래로 스크롤).
- R2 대응한 상담원 정보가 표시되어야 한다. 지금은 '상담원'으로만 나온다.
- R3 자동답변도 상담원 답변 위치(오른쪽)에 보여야 한다. 배경색을 다르게 하고 '자동응답'으로 표시한다.
- R4 오른쪽 패널에 대응한 상담원 목록을 보여준다. AI 응대 뒤 어떤 상담원에게 배정·이관되었는지 이력을 볼 수 있어야 한다.

**/work-log**
- R5 작업로그에서 상담원 내용과 고객 내용이 구분되어야 한다.

**/customers**
- R6 탭 이름을 '기업고객 | 일반고객'(customer(company) | customers(personal))으로 바꾼다.
- R7 일반고객 상세 화면이 필요하다. 최초 접속일(최초 대화 세션 시작), 유입 채널, 이름, 연락처, 이메일, 메모 등 기본 인적 정보를 보여준다. 각 플랫폼 API 연동에서 받은 최소 정보를 보관한다.

**/history**
- R8 목록에 고객명과 상담원(마지막 상담원)을 표시한다.

## AS-IS (코드·스테이징 실측)

### 라이브챗 `apps/web/src/domain/live-chat/LiveChatPage.tsx`

| R1 | 대화 영역(`role="log"`, 1151행)에 ref와 스크롤 로직이 **전혀 없다**. 그래서 열면 맨 위(가장 오래된 30건의 첫 줄)에 머문다. 스크롤 효과는 찾기 결과 가운데 맞춤(418행) 하나뿐이다 | API는 최신 30건을 오름차순으로 준다(`agent.service.ts:900`), 5초 폴링 |
| R2 | 상담원 말풍선 라벨은 `senderName ?? '상담원'`이다. API의 `resolveSenderNames`가 `users.name`만 보고 비어 있으면 건너뛴다(`agent.service.ts:1361`). **스테이징 실측: 사용자 이름이 비어 있는 계정이 대부분이다.** go2joy는 12명 중 11명, 테넌트 3·5·6은 전원이다. 상담원 메시지 중 go2joy 38/38건, 테넌트 3의 48/48건이 이름 없음 → '상담원'으로 표시된다. 보낸 사람 id(`sender_id`)는 모두 들어 있다 | 대화 이력은 `name \|\| email`로 대체하고 있어 표기가 서로 다르다 |
| R3 | AI·시나리오 답변(`sender_type=ai`)은 **이미 오른쪽**이다(`outbound = agent\|ai`). 다만 배경이 연한 보라(`primary-500/10`)이고 라벨은 하드코딩된 "AI"뿐이다. 그래서 상담원 말풍선(진한 보라)과 성격 구분이 약하다. **시스템 자동 안내**(인계 안내·종료·재연결 안내 등, `sender_type=system`)는 고객 말풍선과 같은 회색으로 **왼쪽**에 나온다 | 1177·1208·1225행 |
| R4 | 헤더에 현재 담당자 1명만 나온다(`assignedTo`). 대화 단위의 이력 API는 없다. 데이터는 있다. `assignments`(배정·이관·해제, 유형 auto/manual/transfer, 배정한 사람), `audit_logs`(`agent.conversation_assigned`·`agent.handed_back`·accepted·ended), `agent_alerts`(상담원 연결 요청 사유·시각·확인자). 스테이징 `assignments`는 41행이다 | 수락(accept)이 이전 active 행을 닫지 않는다(`agent.service.ts:1130`) |

### 작업로그 `/work-log`
- 감사 로그(`audit_logs`)의 상담원 행동 목록이다(수락·메시지 발송·고객 연결·종료·열람). **메시지 본문은 감사 로그에 저장하지 않는다**(설계상 보존 기간이 다름). 그래서 화면에 고객 내용도 상담원 내용도 없다. 대상은 "conversation 77" 같은 텍스트이고 열어 볼 수 없다.
- 대화 기록 보기(`ConversationTranscript`, 대화 이력 상세에서 사용)는 역할별 색이 있다. 다만 상담원 말풍선은 이름만 있고 '상담원' 라벨이 없으며, 고객 말풍선에는 고객 이름이 없다.

### 고객 `/customers`
- 탭: 전체 | 기업고객 | **부킹고객**(ko). en은 All | Business customers | Booking customers.
- 일반고객 상세 화면이 없다(기업은 `CompanyDetailModal`이 있다).
- `customers` 테이블: 이름·이메일·전화(암호화), Shopify·Cafe24·외부(identify) id, 유형, 등급. **메모 없음, 최초 접속·유입 칼럼 없음, 어느 플랫폼에서 왔는지 기록 없음.** Woo·Haravan·Odoo 동기화는 고객 id를 고객 행에 남기지 않는다(주문 캐시의 `member_id`에만 있다).
- 최초 접속과 유입은 기존 데이터로 계산할 수 있다. `conversations`(customer_id·channel·created_at)와 `sessions`(first_opened_at·landing_path·channel)을 쓴다. UTM과 referrer는 저장하지 않는다(landing_path는 쿼리 제거).
- 개인정보 열람은 `CUSTOMER_PII_REVEAL`와 감사 기록 경로가 이미 있다(`GET /customers/:id/reveal`). 수정은 이름·등급만 가능하다.

### 대화 이력 `/history`
- 목록에 고객·담당 상담원 **칸은 이미 있다**. 비어 보이는 이유는 두 가지다.
  - 고객명은 `sessions.customer_id`의 이름만 쓴다. claimed 대화의 고객, 별칭, 기업명, identify 이름은 대체로 쓰지 않는다.
  - 상담원은 `conversations.agent_id`만 쓴다. AI로 반환하거나 종료하면 이 값이 비워지므로, 응대했던 대화도 빈칸이 된다.

## 제약
- 다중 테넌트: 모든 새 조회는 `tenant_id`로 필터한다.
- 개인정보: 이름은 평문 표시(10/23 결정). 이메일과 전화는 마스킹하고, 원문은 `CUSTOMER_PII_REVEAL`과 감사 기록 경로로만 본다. 메모는 개인정보가 들어갈 수 있으므로 암호화 저장하고 DSAR 삭제 대상에 넣는다.
- 상담원(운영자) 이메일은 고객 개인정보가 아니다. 테넌트 내부 표시용 대체 이름으로 쓸 수 있다.
- 스키마 변경 시 스테이징은 `DB_SYNCHRONIZE=false`이므로 SQL을 먼저 적용한다. PR에 `## Migration` 섹션을 넣는다.
- 모든 문구는 i18n 6개 언어로 넣는다. 저장·수정은 토스트로 피드백한다.
